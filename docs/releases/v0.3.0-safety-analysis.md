# v0.3.0 safety analysis and prefill follow-up

## Verdict

**The original v0.3.0 prefill path is not ready for broad rollout. With the guards in [#118](https://github.com/Arkiv-Network/arkiv/pull/118), the two reproduced startup/retry blockers are addressed for fresh deployments.**

The operational verdict remains conditional: validation also reproduced a separate native abort during SIGINT shutdown with optimized binaries limited to two CPUs, on both the original code and #118. That issue is unresolved; this report does not certify reliable graceful shutdown or unconditional production readiness.

The [follow-up review](https://github.com/Arkiv-Network/arkiv/pull/117#pullrequestreview-5161217660) reproduced two P1 findings: nodes could start and produce blocks after a skipped or failed import, and a rejected retry could delete an already imported datadir's genesis changesets. The earlier unconditional "safe, no blocking findings" assessment is withdrawn. These failures occur during fresh provisioning, so excluding in-place upgrades does not exclude them.

| Deployment | Assessment |
| --- | --- |
| Fresh ordinary alloc-based genesis | Low risk within the reviewed scope; no new consensus defect found. |
| Prefill on the original v0.3.0 code | Successful imports work, but startup and retry hazards block a broad rollout recommendation. |
| Fresh prefill using the #118 fix | The two startup/retry findings are fixed. Import successfully before startup; use a fresh datadir after a failed or interrupted attempt. The separate SIGINT shutdown finding remains unresolved. |
| Existing seeded datadir or in-place upgrade | Not covered by a migration or upgrade safety claim. Older imports lack the completion record and are refused by the new guard. |

The fix is a follow-up to v0.3.0; it does not change the code at the original release commit. The unresolved shutdown finding and the remaining operational and coverage follow-ups are listed separately below.

## What this covers

`main` moved from `0fd58ce` (v0.2.1) to `0a5e349` (v0.3.0) in two commits:

- `068acf7` — the offline genesis seeding work (#112). 39 files, 6516 insertions, 62 deletions.
- `0a5e349` — the workspace version bump (#116). A version string and the 16 matching `Cargo.lock` entries, nothing else.

Of the 39 files in `068acf7`, 17 are new and 22 are edits to files that already existed. The new files include `crates/arkiv-seed`, the `init_state` module, tests and experiment scripts. The review covers both running-node behavior and provisioning failure paths: an opt-in importer can leave persistent state that a later normal node startup consumes.

The corrective implementation is #118, with production changes at `10be090` and the final regression test at `a74e307`. It adds durable import status, startup and retry guards, regression tests and provisioning documentation. It changes no executor or committed-store state-transition code and adds no dependency versions.

## The deployment assumption this rests on

**Existing deployments are not upgraded in place.** Every node on this line comes up on a fresh genesis, either an ordinary empty/dev genesis or one pre-seeded by `arkiv-seed`. No datadir migration path is provided or claimed.

That assumption is load-bearing. It removes a class of risk from consideration: the chain pruning map gains three SQLite tables and a startup bootstrap step, and `init-state` changes how block 0 is written. Against a pre-0.3 datadir none of that is exercised or tested, and this release does not ask it to be. Everything below is about whether a *fresh* node behaves correctly, in both of its two supported shapes.

The new guard deliberately refuses older prefilled datadirs without its completion record, even if they have already advanced beyond genesis. Re-provision fresh deployments from the original dump into a new datadir; this is not an in-place upgrade procedure for an existing seeded chain. Do not bypass the guard by fabricating a record. The progress JSON is advisory and cannot authorize startup.

## Method

Each review read the diff hunk by hunk against the current files and was asked to prove claims from the code rather than from commit messages. Continuous integration on the bump commit passed all five checks: build, tests, lint, Python formatting, and a Kurtosis sequencer-plus-follower smoke test.

The follow-up used the exact #117 CI binary, whose source tree matched the reviewed head, to exercise a correct import, skipped import, a syntactically valid truncated dump, and a rejected retry. The valid case served 40 genesis entities and later purged them at expiry. Both skipped and failed imports instead produced blocks while serving zero genesis entities. A wrong-root retry deleted all eight changeset files and led to persistence errors on shutdown. These are local provisioning/recovery failures; the probes do not establish a remote exploit or a defect in normally initialized block execution.

Validation of #118:

- `cargo test -p arkiv-reth --locked` at `10be090`: **41 passed** locally, covering ordinary node operations, recovery, seeded genesis and the new safety regressions. After the CI shutdown finding, all **4 updated safety tests** passed locally at `a74e307`; the production implementation is unchanged between those commits.
- `cargo clippy -p arkiv-reth --all-targets --locked --no-deps -- -D warnings`, formatting and diff checks passed.
- Process regressions reject skipped and failed imports in both storage layouts, preserve all eight changeset files byte for byte after rejected retries, and verify correct block production followed by forced-stop/restart recovery from persisted history. This does not claim a clean SIGINT shutdown.
- Database tests reopen an incomplete attempt record and reject missing, malformed, mismatched or unsupported-version completion data.
- An additional real-process SIGKILL probe interrupted an import after the durable attempt record. Producer startup, follower startup and a retry were all rejected.

## Block production and the pruning map

**The pruning map cannot cause a wrong block.** This is the structural fact that governs every severity call in this area. The executor re-derives expiry from real state and skips any key that is not actually expired: a missing entity is skipped, and so is one whose expiry is still in the future. The map is a candidate hint. Nothing it gets wrong — stale, saturated, partial — can produce an incorrect state transition. The worst outcome is a purge key that costs calldata and does nothing, or a purge that happens later than it could have.

**On an ordinary empty genesis the new bootstrap is a no-op, traced end to end.** First start reads the bootstrap flag, opens a block-0 state snapshot, and performs a single account-code read of the `$all` bucket. No such account exists, so the bitmap is empty and the walk returns before the writer connection is opened and before any large allocation. The flag is then set unconditionally, so every later start short-circuits. Net first-start cost is one extra SELECT, one account-code lookup and one UPDATE.

**Returned catch-up errors are logged and retried; task placement is not a blanket panic guarantee.** Startup catch-up runs on a regular task. Canonical-notification catch-up is awaited by the payload service, which runs on a critical OS thread. Bootstrap worker and blocking-task joins convert their failures into errors, but that does not prove every possible panic is isolated from node shutdown. The original claim that both call sites were non-critical was incorrect.

**Interruption handling is correct against the actual SQL.** The upserts and the cursor update share one immediate transaction, and the upsert is a real conflict-update, so replaying a batch is harmless. Ids are consumed in ascending order, so the cursor bound dominates every entry in the batch it commits with. A crash between the last commit and the flag write is also safe: the next run finds a cursor past the highest id, matches nothing and completes. The walk deliberately never touches the watermark, so the per-block replay stays authoritative over anything the walk recorded.

**The bootstrap bounds snapshot lifetime by chunk work.** The walk runs inside one blocking task; worker threads perform synchronous reads through an immutable provider reference and open snapshots per chunk rather than holding one for the entire seed. A sufficiently slow chunk can still hit the read-transaction timeout. The update lock serializes the SQLite writers and is not re-entered. Blocking on the runtime handle inside a blocking task is the pattern already used in v0.2.1.

**Arithmetic is clean.** Entity ids are allocated densely from a zero-based counter with no free list, so the cursor increment cannot approach the type's limit; a conversion that errors would catch it before anything could be persisted. Every count crossing the SQLite boundary goes through a checked conversion in both directions.

**Nothing on the block path changed.** Payload construction, the protocol transaction, the purge envelope, the update collection and the selection query are byte-identical to v0.2.1. Purge gas is unchanged, and the executor recomputes it from real state regardless.

## Consensus: the store and the chain spec parser

This is the section that mattered most, because this crate decides how entity state is laid out and how the state root falls out of it. A change here would fork every chain.

**There is no consensus-visible change against v0.2.1 for a chain with an ordinary genesis.** Established two ways.

By reading: the store diff is five added imports, three functions changed from private to public with byte-identical bodies, one block of new code inserted after an existing function's closing brace, and three new tests. The function block execution calls is untouched. The files holding key derivation, address derivation, encoding and index layout are not in the diff at all, and their golden pinned-address vectors still pass.

By executing: a probe compared the new parser against the exact v0.2.1 expression for a genesis carrying a real alloc with balances, nonces, code, storage and custom header fields. Genesis hash, state root, full header, hardforks, minimum base fee and chain id all matched exactly. The empty-alloc case matched too.

Two new store functions exist for the bootstrap to read block-0 state. They are one-line delegations to existing code and perform no writes. A third is a genuine bulk write path, but its only non-test caller is the offline seeder; block execution cannot reach it.

**Root checks alone did not make provisioning safe.** A `stateHash` alongside a non-empty alloc is a parse error, and malformed values fail deserialization. The importer checks the declared dump root and the computed root, but it commits state in chunks before the computed-root check. On the original release, failure could therefore leave partial state behind, and normal node startup did not require a successful import. #118 adds the completion gate described below; it does not make the chunked import atomic or resumable.

## Prefill findings and their fixes

1. **P1: skipped or failed import could produce blocks on the wrong state.** The original startup accepted an initialized genesis header without checking whether the asserted state had been imported. #118 writes a versioned `ArkivGenesisImport` record in MDBX, bound to both the genesis hash and state root. It commits an incomplete attempt before importing and marks completion only after the state writes and computed-root validation succeed. The node checks completion before constructing networking, payload-building or pruning-bootstrap components. Missing, incomplete or invalid records fail closed in both storage layouts.

2. **P1: a rejected retry deleted existing genesis changesets.** The original command cleared the v2 changeset segments based only on empty genesis `alloc` and a block-0 tip; those conditions also hold after a successful import. #118 validates the dump's first-line root and rejects preexisting state or an earlier attempt before deletion. The v2 importer also finishes parsing before clearing the empty genesis entries. Regression tests verify the original successful changeset files remain byte-for-byte intact, the node subsequently produces blocks, and persisted state/history survive a forced stop and restart.

An unreadable dump or invalid first-line root can be corrected before an attempt begins. Once the attempt is recorded, any failure or interruption requires a fresh datadir. No automatic deletion, rollback, resume or upgrade migration is provided. The [provisioning instructions](../../README.md) gate node startup on a successful `init-state` command.

## Unresolved SIGINT shutdown finding

The [initial #118 workspace test run](https://github.com/Arkiv-Network/arkiv/actions/runs/34421333355/job/102697202386) failed because the node aborted during SIGINT shutdown with `pthread lock: Invalid argument`. The diagnostic comes from RocksDB's native pthread wrapper. The build, lint and sequencer/follower smoke test on that head passed, but the local unoptimized test result was insufficient to establish graceful-shutdown reliability.

An independent probe successfully imported 40 entities, started a dev producer with a 500 ms block interval under `taskset -c 0,1`, waited for block 2 and sent SIGINT. The native abort reproduced **3/3 times on the original #117/v0.3.0 binary and 3/3 times on the #118 binary**. Both were CI `dev-fast` artifacts. This establishes that the failure predates the guard fix; its underlying shutdown/lifetime cause and its full operational impact have not been established.

The retry regression now follows the repository's existing crash-recovery tests: advance 20 blocks beyond the initial tip to get persisted history, kill the process, restart on the same datadir and verify genesis state, the persisted tip and subsequent production. It still rejects persistence-service errors. This change tests the retry fix without asserting that an unrelated shutdown path is reliable. It does not fix or waive the native abort, and these probes do not prove that every abort preserves all state. A shutdown fix and focused durability validation remain necessary before making a broader operational safety claim.

## Binaries, dependencies and infrastructure

**No new third-party code enters the tree.** The lock diff for #112 is 38 added lines and zero removed. The only new package entry is the local `arkiv-seed` crate. Every new dependency line resolves to something already locked: reth crates on the same git pin the workspace already used, and alloy, serde and tempfile crates already present. The SQLite binding stays on its exact pin. No version moved, no build script was added, nothing pulls native networking.

**Import execution is opt-in, but its persistent effects matter to startup.** `init-state` selects the custom command, and the streaming importer handles block 0 under storage v2, with reth's importer handling other layouts/blocks. The original non-fresh-datadir check was insufficient: changesets could already have been deleted before rejection. #118 guards genesis imports in both layouts and checks completion during normal node-component construction. The importer's state write targets, account-then-slot ordering, trie walk and root checks remain unchanged. Later-block snapshot importer dispatch remains with reth; that does not supply a migration for an older seeded datadir.

**Exactly one default changed for a normal node.** The file log filter moves from `debug` to `debug,turso_core=info,turso=info`. That is strictly quieter. It silences roughly 500 trace and debug call sites in the SQLite layer while leaving every INFO, WARN and ERROR intact, and the rotating-file cap of about 1 GB is untouched. It remains overridable by flag as before. No existing flag was renamed, removed or redefined.

**Seeding is opt-in and the images are untouched.** The Kurtosis helper reads its seed count from the environment with a default of zero, and on zero it uses the committed chain arguments file unchanged. The release workflow builds from two Dockerfiles this change does not modify; the one Dockerfile it does touch is the prebuilt image used only by the local and CI devnet, and its new base-image argument defaults to the previous literal. No CI step was made non-blocking.

## Remaining operational and coverage follow-ups

The two fixed prefill findings and the unresolved shutdown finding above are separate from these additional operational and coverage items.

1. **A persistently failing bootstrap prevents pruning.** The replay loop sits behind the bootstrap gate, so a bootstrap that always fails means pruning never starts, with warnings as the operator signal. Deleting the pruning database on a long-running node whose required historical state has been pruned can cause this. The tested fresh-genesis flow retains that state; improved error reporting and a defined recovery procedure remain follow-ups.

2. **The bulk seeding path and the per-entity path do not produce identical state.** They agree on the entity records, and the seeder is deterministic for the complete seed specification, including batch size. But the two lay out the tier-2 range-index trees differently, measured at 351 versus 441 slots on an 80-entity probe. The bulk path is offline-only. Reusing it on the block path would require a separate consensus review. The current equivalence test compares only one of the two backing maps and should not be treated as proof of identical full state.

3. **The Kurtosis smoke test now always seeds.** The empty-genesis devnet path no longer has devnet coverage and is exercised only by the Rust suite. A coverage gap rather than a defect, but empty genesis is one of the two shapes this release supports, so it should get its own matrix entry.

4. **The bootstrap holds its lock for the whole walk.** On a large seeded genesis that can be hours, during which canonical-state notifications back up and the receiver lags. The stream treats lag as a skip rather than an end, and those notifications warm a payload pre-cache. The reviewed consequence is a cold cache during the walk rather than a demonstrated block-production stall; large-seed operational behavior still warrants monitoring.

5. **Smaller items.** A 48 MB batch buffer is reserved eagerly for any non-empty genesis, however small. Two resolver bindings open separate state snapshots and should be named to make that purpose clearer. A `stateHash` explicitly set to null is treated as absent. Unsupported chain names fail with a misleading file-not-found message. The import writes a progress file into the datadir with no way to turn it off.

## A v0.2.1 bug this release fixes

An entity created with `expiresAt = u64::MAX` is documented as never expiring, and any user can create one. On v0.2.1 the pruning map rejected that value as out of SQLite's integer range. That failed the map's per-block update, froze its watermark, and — because selection requires the watermark to match the parent block — stopped expired-entity purging for the whole chain from that block onward, permanently.

Such expiries are now stored saturated. The row is kept and can still be updated, and it can never be selected: the selection query is bounded by the block height, that bound is itself range-checked, and no chain reaches the saturation point. Even in that impossible case the executor's independent re-check would skip the key.
